# Document storage and report archive implementation

Updated November 10, 2026.

## Delivered behavior

- **EDMS** has custom category storage tabs, organization submissions to SAS, modal review actions, and SAS broadcasts. It does not contain AP, PAR, or FL storage tabs.
- **Reports & Analytics** holds approved AP PDFs, PAR PDFs, and FL XLSX files. SAS sees archive storage within each corresponding analytics tab; officers have the three report storage tabs for their selected organization.
- Officers can read, submit, and download only their own organization's documents. SAS internal files remain SAS-only. Broadcast delivery remains a separate inbox with recipient/read tracking.
- Category creation is shared by broadcasting, EDMS storage, and Settings. Names are validated and protected against simultaneous duplicates; rename, recolor, deactivate, archive, and reactivate preserve category IDs and historical references.
- The last broadcast category option opens Add Category and selects the newly saved category without losing the draft. Attachments are optional for broadcasts and remain required for officer submissions.
- Officers / Req. remarks category switches, Standard Categories buttons, and automatic category seeding have been removed. Return/rejection remarks are required globally.
- Approved report files are generated from the existing official templates, persisted with frozen source/dependency snapshots, and retried through durable jobs. Receipts and photos are supporting files rather than substitutes for the actual approved report.
- PDF preview uses a paginated canvas viewer, including browsers without a native embedded PDF viewer.

## Principal code

| Area | Location |
| --- | --- |
| General/custom storage and shared report file browser | `src/app/modules/documents/components/EdmsStorage.tsx` |
| Reports & Analytics archive entry point | `src/app/modules/reports/components/ApprovedReportStorage.tsx` |
| Document preview, category creation, modal review | `src/app/modules/documents/components/` |
| Backend authorization, category operations, protected files, archive jobs | `functions/edms.js` |
| Shared classification, ownership, category and tab policy | `functions/edms-domain.mjs` |
| Approval triggers, job execution, bounded recovery | `functions/index.js` |
| Shared official report rendering bundle | `functions/report-renderers.ts`, generated by `scripts/build-edms-renderers.mjs` |
| Firestore and file authorization | `firestore.rules`, `storage.rules`, `firestore.indexes.json` |
| General document and historical report migration | `scripts/backfill-edms.cjs` |

`documents` and `edms/` are for EDMS. `report_archives`, `_report_archive_jobs`, and `reports/` are for approved workflow archives. General category names never classify workflow documents. Old workflow metadata in `documents` is filtered out of EDMS and exposed through report compatibility readers until backfill finishes; migration preserves that metadata for history.

## Production rollout

Production deployment and data migration have not been performed by this implementation task.

1. Install the root and Functions dependencies and run the verification commands above.
2. Confirm active officer/adviser/signatory records use the same normalized email as their Firebase Auth identity. EDMS authorization deliberately does not accept a local-storage role or organization claim as proof of membership.
3. Deploy the checked-in Firestore indexes and wait for them to become ready. Deploy the backend Functions and protected Storage rules using the existing project/codebase. The Functions predeploy hook builds the shared report renderer automatically.
4. Publish the web build through the project's existing hosting pipeline during the same rollout window. Existing clients should refresh to use the new backend document operations and protected-file readers.
5. Review the migration inventory using the project's authorized administrator credentials:

   ```powershell
   node scripts/backfill-edms.cjs --project sti-sync
   ```

   This is a dry-run. Review duplicate categories/archives, missing owners, and ambiguous legacy source links before applying changes.

6. Apply the reviewed migration:

   ```powershell
   node scripts/backfill-edms.cjs --project sti-sync --apply
   ```

   The script copies general files to protected storage, reconstructs approved report archives in the separate report collection, and repairs source backlinks. It is safe to rerun. It preserves historical metadata and original provider files rather than deleting them. Historical reconstruction uses the currently available source data when an original approval-time snapshot does not exist.

7. Enable the tightened Firestore rules after the backend, indexes, and compatible web readers are available. Verify with a real SAS account and officers from two different organizations. Check that report creation completes and production signed downloads work; the Functions runtime identity needs permission to sign download URLs for the configured bucket.

Example deployment commands, issued from the web project root:

```powershell
firebase deploy --project sti-sync --only firestore:indexes
firebase deploy --project sti-sync --only functions:accounts,storage
# Publish the web build and run the reviewed backfill before the final rules cutover.
firebase deploy --project sti-sync --only firestore:rules
```

`EDMS_STORAGE_BUCKET` can override the configured storage bucket for the backend and migration. The default production bucket is the one already initialized by this project.

## Reproducing browser checks locally

Start Auth, Firestore, Storage, and Functions emulators using project `demo-sti-sync`; run the web dev server with `VITE_FIREBASE_EMULATORS=true`. The local-only `scripts/seed-edms-preview.cjs` creates disposable SAS and Alpha/Beta officer accounts and sample records when emulator host variables are set. It refuses to run without those variables. No production credentials or production data are needed for these checks.
